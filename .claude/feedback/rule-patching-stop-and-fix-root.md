# 规则连续打补丁，要先追根源止损

**问题描述**：2026-11-07 用户截图说「分包商要有未选择分包商的下拉选项」，起初选的是「只是显示一致」；同日改成「能点，点了清空分包商」。此后 REQ-NODE-002 两天内修订 6 次：清空后导入以看板为准 → 单站 Reset 加「分包商按文件覆盖」勾选 → Not started 的站跟文件 → 2026-11-08 文件空不覆盖已完成站。中间为清空补了撤回封住、簿记行等逻辑，e26c70e、7ca2136、9db58dc 三个提交共改 600 多行。2026-11-08 用户在 ai-ts 勾「按文件覆盖」导入分包商全空的文件，6 个已完成的站变成「完成但没有分包商」。主 Agent 照例又补一条规则（Spec v1.37），用户随即纠正：
- 「这就是开始丢了一个无分包商选项惹的祸，必要止损，要从源头修改，不是一味的修正，顺从」
- 「开始丢了无分包商，惹了很大祸」

**触发场景**：把某个值做成可操作选项（「未选择」可点、点了清空）后，「空」同时表示三件事：文件没写、人主动清空、被导入覆盖。含义分叉后，导入更新 / 替换、撤回、Reset、手改每条路径都要各自约定怎么处理空，每修一条就在别处冒出新边角状态。我每次只看眼前症状补一条规则，没有回头看这是同一个根在长新芽；用户怎么提我就怎么加。

**教训/建议**：
1. 同一条规则连续第 2～3 次修订、每次都是新边角状态时，停止补条款，先追根源：是哪个设计让状态含义分叉了。
2. 给用户的是止损方案：撤掉或收窄那个设计，用一条不变量统一约束所有路径，并说清代价；不要再递一条补丁让用户批。
3. 用户第一次提出要「把某个值做成可操作的选项」时，先讲清它会让哪些已有路径（导入更新 / 替换、撤回、Reset、手改）都要重新定义，以及代价，再让用户选；不要只按字面答「好」并把「只是显示一致」当成小改。
4. 不是「用户怎么说就怎么加规则」：用户的提法是需求输入，影响面由我先摸清并讲出来。
5. 用户说「源头」时不要凭猜理解，先查证历史上哪一步造出了错误状态。这次主 Agent 起初把源头理解成「加了 No subcontractor 选项」，用户的意思其实是「缺了空状态，导致默认选了第一个供应商」；查证结果是解析器沿用上一站的 Subcon（7ca2136）。止损分析的第一步是查提交历史与代码，不是推断。

**适用范围与例外**：所有需求迭代，尤其是导入、撤回这类多路径相互作用的字段。独立、与其他路径无交互的小改动不必走这套。
