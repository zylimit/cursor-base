# 分批写说明、提模块划分的派单怎么写

存量项目一次补齐时，说明少则几十段、多则上千段，主 Agent 不自己逐张写：按分组（数据库）或按层（模块）分批，一批一个 fresh 的 Sub-Agent。它不继承会话，派单里没写的它只能猜。下面三份是在一个 79 张表、六百多个代码文件的真项目上用过的写法，尖括号里的换成本项目的；别的句子尽量照留——每一句都是为了挡一种实际出过的错。

跟着开发走的项目用不着这一份：一个 Task 加一两张表、几个文件，改的人自己写。

## 先后

1. 先写整库的导读与各组的导读（`doc:db`、`group:<组 id>`），再铺表——后面每一批都拿它对齐叫法。
2. 挑一个分组做小样（三到五张表，表与列写齐），用户看过点头，再铺开。小样里写得好的两张表当范例，后面每一批都指给它看。
3. 铺开时一批一个分组、三到八张表，几批可以同时跑——各写各的锚点，互不影响。
4. 模块：先提模块划分并铺进 map.json，`build` 之后再分批写模块说明（一批六到十个模块）；`doc:arch` 等模块说明都落盘之后最后写。

## 一、表与列的说明

```
你要给这个项目的数据库设计文档写说明：「<分组标题>」这个分组里 <N> 张表各一段表的说明，加上这些表里每一个缺含义的列的说明。全程用中文。

读者：<谁接手、懂什么、不懂什么。例：两周后接手的 10 人团队，懂数据库与编程，不懂这门业务，没参与过开发，手上没有 AI 编程工具>。

背景：<项目一句话是做什么的>。文档由生成器从建表定义与代码里机械取出表结构、关系、谁写谁读；「这张表是干什么的、这个字段什么意思」只有读懂代码的人写得出来——这就是你的活。你写的经命令落盘，页面上标着「说明 · 草稿」，之后有人抽审。

先读：
1. 写说明的规矩：<项目根>/.claude/skills/readable-docs/SKILL.md 的 [写说明] 一节，全程照它写。
2. 已经写好的整库与各组导读、两张范例表：<路径>——叫法与它一致，详略与口吻照范例。

你负责的表：`<表 1>`、`<表 2>`……
提示：<这一组里最要紧的一两件事。例：`<某表>` 的 `status` 是这组最要紧的枚举，要在代码里把全部取值找全，各用半句话说清是什么>。

材料（都只读）：
- 每张表的上下文：在 <项目根> 下跑 `node .claude/scripts/readable-docs.mjs pending --json > <临时文件>`。`tables[]` 每项有 `table`、`missingColumns`（要你写含义的列的锚点）、`context`（列、来源里的注释、它引用谁、谁引用它、哪些文件写它读它）。`missingColumns` 里的每一个列都要写；没列出来的不用写。
- 源码：<代码目录>。每张表至少读它最主要的写入文件（上下文里的 writers）里写它的那几段，看一行是在什么时候、带着什么值写进去的；枚举类的列在代码里找到全部取值再写；JSON 列看代码往里放了哪些键。别只靠列名猜。
- 业务背景：<需求规格的路径；很大时写明只读哪几段、别的按关键词搜>；口径库 <路径，有的话>。

怎么交：一张表一个文件，放 <你的临时子目录> 下，先是 `## table:<表>` 一段，再是若干 `## column:<表>.<列>` 段。写完一张交一张：`node .claude/scripts/readable-docs.mjs note put --file <文件>`。有一段不合格整批不落盘，照它报的原因改了重交（报「有密钥或内网地址样式的字样」就换个写法）。全部交完再跑一次 `pending --json`，核对你负责的表都不在 `tables[]` 里了。

约束：
- 说明只许经 `note put` 落；不直接编辑 docs/readable-src/ 下的文件，不跑 `build`，不改代码。
- 只写你这一批的表与列。
- 例子一律合成：不出现真实的地名、人名、客户名、设备编号、数量。要举名字就编一个明显是假的。
- 拿不准的写「待确认：……」，不编、不猜。
- 不联网，不把代码与文档内容发到外部服务。
- 临时文件放你自己新建的子目录，收尾只删它。工具调用 <60> 次以内。

交回来（简短）：
- 每张表一行：写了几个列、主要依据了哪几个文件。不贴说明全文。
- 所有「待确认」，各一句为什么拿不准。
- 代码里看到、但与来源里的注释或需求规格说法不一致的地方，各一句带文件名；看着没人用的表或列也列在这里。没有就写没有。
- 最后一次 `pending --json` 的核对结果。
```

## 二、提模块划分

平铺的目录（几百个文件在同一层）机械分不出模块，要 AI 提、人确认。这一单是分析，不写代码。

```
给这个项目提一份「模块划分」的提议，供人审。全程用中文。

读者与用途：<谁接手>。架构师要的第一张图是「系统由哪几块组成、谁依赖谁、每块管什么」。

要交的东西（都放 <你的临时子目录>）：
1. `modules.json`：`{"layers": [...], "modules": [{ "id", "title", "layer", "paths": [通配…], "status": "proposed" }]}`。`id` 只许小写字母、数字、连字符；通配里 `*` 不跨目录、`**` 跨目录；一个文件归第一个匹配它的模块，所以窄的写前面、宽的写后面；模块的先后就是页面上的阅读顺序，按新人该读的顺序排。
2. `rationale.md`：每个模块一行——id、标题、层、文件数、接口数、读写的表数、为什么这些文件算一块（一句话，讲业务，不讲文件名的规律）；后面写拿不准的几处（哪些文件放哪边都说得通、选了哪边、为什么）、循环依赖有哪几组、建议人重点审的地方。
3. 建议往配置的 `ignore` 里加的通配（与代码放在一起的测试文件、生成物）。

怎么做：
- 在副本上做：`cp -r <项目根> <你的子目录>/proj`，原目录不动。
- 取事实：`node .claude/scripts/readable-docs.mjs build --facts-json --root <副本> > facts.json`。`code.files[].head` 是文件头说明的原文——判断一个文件管什么的头号依据；`code.edges` 是文件之间的引用；`code.routes` 是接口；`usage` 是每张表被谁写谁读；`groups` 是表的业务分组；`arch.modules` 是现在（按目录分或上一版划分）的汇总。
- 项目自己有架构文档或模块登记的（<路径>），先读：提议与它不同的地方在 rationale 里说清。
- 标题用需求规格里现成的叫法，是接手的人在需求里见过的词，不是文件名的翻译。

划分的标准，按重要性：
1. 一个模块对应业务里的一件事，看标题就知道它管什么。接口路径的前缀、读写的表属于哪个业务分组、文件头说明里讲的事，三样互相印证；文件名的前缀只是辅助。
2. 公共的支撑代码（数据库连接、鉴权、配置）单独成模块，不塞进某个业务模块。
3. 一个模块超过四十个文件多半还能拆；只有一两个文件的要有理由（入口、配置）。
4. 把你的 `modules.json` 铺进副本的 docs/readable-src/map.json 再 `build`：报数行里「未归属的文件」「项目判断里对不上的」都是 0 才算分完；循环依赖、越层引用照实抄进 rationale——不要为了消掉循环把业务上不相干的文件硬凑到一起，循环是事实。

边界：`status` 一律 `proposed`；拿不准的照实写，不为显得完整而硬下结论；不改原目录，不联网；工具调用 <70> 次以内，读文件头说明用脚本批量打出来看。

交回来：分了几个模块、几层，每个一行（id、标题、文件数）；`build` 报数行里架构那一行的原文；拿不准、要人重点审的三到五处；产物的路径。
```

主 Agent 收到后：把 `modules.json` 并进 map.json（表的分组那几项不动），`build`，核「未归属」与「对不上」是 0、循环与越层的数与它报的相同，再向用户报——几个模块、几层、哪几处拿不准、与项目旧架构文档哪里不一样。

## 三、模块说明

```
给这个项目的 <N> 个模块各写一段「模块说明」，会出现在给接手团队看的架构文档里。全程用中文。

读者：<同上>。文件、接口、引用关系、读写的表，生成器已经从代码里取出来放在页面上了，不用你复述；你写的是把这些事实串起来的那几句——这个模块到底管业务里的哪件事。页面上它标着「说明 · 草稿」。

你负责的模块：`<id 1>` <标题 1>、`<id 2>` <标题 2>……

材料（都只读）：
1. 每个模块的上下文：`node .claude/scripts/readable-docs.mjs pending --json`，`modules[]` 每项有 `id` 与 `context`（文件与文件头说明的头一句、接口、它依赖谁、谁依赖它、读写的表）。
2. 全部事实：`build --facts-json`。`code.files[].head` 是文件头说明全文，`code.routes[].doc` 是处理函数的说明，`arch.modules[].uses` 里有具体是哪几对文件、用了哪些名字。
3. 划分这些模块的理由：<rationale.md 的路径>。
4. 需求规格 <路径>：按关键词找相关条目读，业务的叫法以它为准。表的说明在 docs/readable-src/notes/ 下，可以借它理解这个模块碰的表。
5. 真要弄清一件事时再打开源码读——先看文件头说明，够了就不必读代码。

怎么写：每个模块一段，以 `## module:<id>` 开头。
- 第一段只写一句话，不超过 60 个字——这个模块管业务里的哪件事。清单页拿它当这一行，单独拿出来也要读得懂，不以「本模块」开头。
- 后面三到六句，按需要写（没话说的不凑）：它管到哪为止、和相邻的模块怎么分工；一次典型的事从哪进、到哪出；哪些表主要由它写；改它要小心什么。
- 规矩照 SKILL.md [写说明]：先讲业务再讲技术；每句话指得到出处，拿不准写「待确认：……」；不复述文件清单与接口清单；不写开发史；例子合成。
- 不描述页面当下的样子（「入口一栏是空的」「被列进某张清单」）——页面跟着代码与生成器变。
- 提到别的模块用它的标题。

写的时候发现代码、文件头说明、需求规格对不上的地方，或者某个文件明显不属于这个模块：不悄悄按一边写，单列出来交回。第一句话写不顺的模块（说不清它管什么，或者得并列几件不相干的事才写得全）同样单列——多半是划分的事，不拿一段绕的说明把它盖过去。

交什么：
1. 说明写进一个文件 <路径>（主 Agent 统一 `note put`；你不跑会写盘的命令）。
2. 同目录一份发现的问题：对不上的地方、你认为放错模块的文件、「待确认」各是什么。没有就写「无」。
3. 最后一条消息：每个模块的第一句、「待确认」共几处、发现的问题几条、两个文件的路径。不贴全文。

边界：不联网；临时文件放你自己新建的子目录，收尾只删它；工具调用 <45> 次以内。
```

## 主 Agent 收回来之后

- `pending` 看缺口是不是清了，`build`、`check` 到「不一致 0 条」。回执里的「0 条」不当数，亲跑。
- 每批抽一两段对着代码核：说明里讲的写入时机、枚举取值、谁调谁，代码里是不是这样。
- 「待确认」收齐：能在真实仓里查实的当场查实、把那句改成确定的说法再 `note put`；查不实的列给用户。
- 各批「发现的问题」并成一份交给用户，注明未经人核实。不替用户判哪条是缺陷。
- 交回来说「第一句写不顺」的模块：先回头调划分（map.json 里拆开，或把放错的文件归到该去的模块；调是因为原来分错了，不是为了让循环依赖、越层引用的数好看），`build` 之后重写那几段；代码本身该拆而这一轮动不了的，进「发现的问题」。
- 写说明用的是源码副本时，副本要与真实仓一样齐全（设计文档、接口约定、部署配置都在）；副本里缺文件写出来的「待确认」，回到真实仓里查。
