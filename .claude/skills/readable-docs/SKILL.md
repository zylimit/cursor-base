[任务]
    给项目出一套浏览器直接能开的工程文档，写给没参与开发、手上没有 AI 的人看。事实由 `.claude/scripts/readable-docs.mjs` 从建表定义与代码里机械取出，AI 只写机器取不出来的说明——表的用途、字段的含义、模块管什么，分组、整库与整个系统的导读；说明经命令落盘并盖指纹，来源变了自动标「待更新」。现在做完的是数据库设计、人读版需求规格与架构设计，算法设计、测试设计在后面几期。
    文档只由来源生成、被来源刷新，`docs/readable/` 不手改；交出去之后对方手改了，不回写、不再保证同步。
    文档即代码：页面是代码结构照出来的样子。说明写不顺、模块之间绕成环、有文件哪个模块都放不进、一张表谁都在写——都不是文档的毛病，是设计不合理、架构在变坏。文档不替代码遮丑：照实出、照实标，看出来的问题交出去，不在说明里把它说圆。
    两种走法。**跟着开发走**：需求规格一生成就出人读版，之后每个 Task、每次提交、每个 Phase 各带着文档的那一份，不靠谁记着说一句「出文档」，见 [跟着开发走]。**存量项目一次补齐**：项目已经写了一大半才来补，照 [第一次] 走，先出小样再铺开。
    参考文件按需读：references/dispatch-templates.md（分批写说明、提模块划分的派单怎么写）、references/sample-notes.md（说明的范例与不要怎么写）、references/reading-the-numbers.md（报数行与核对结果怎么读、各该怎么办）。

[依赖检测]
    必需：本机有 node；项目里有建表定义（`.sql`，PostgreSQL 方言）。没有建表定义就出不了数据库设计，如实告诉用户，不拿别的东西凑；只要人读版需求规格的，有需求规格就够，`ddl` 留空数组；架构设计只要配了 `codeRoots`、里面有 Python 或 JS 一族的代码就出，不要求有建表定义。
    `docs/readable-src/config.json` 不在 → 新项目、照常开发的项目走 [跟着开发走] 的起头那一步；用户要一次补齐存量的走 [第一次]。

[文件结构]
    docs/readable/                  生成的页面，入库，不手改
    docs/readable-src/config.json   来源在哪（人和 AI 直接改）
    docs/readable-src/map.json      项目判断：业务分组、运行时表名的归属、模块划分与层（人和 AI 直接改，可以没有）
    docs/readable-src/notes/        AI 写的说明，只经 `note put` 落盘，不直接编辑
    map.json 的写法（哪一项没有就不写，整个文件可以没有）：`{ "version": 1, "tableGroups": [{ "id": "order", "title": "订单与明细", "tables": ["orders", "order_items"], "status": "proposed" }], "dynamicTables": [{ "file": "app/report.py", "reads": ["orders"], "writes": [], "status": "proposed" }], "layers": ["界面", "业务", "数据"], "modules": [{ "id": "ordering", "title": "下单", "layer": "业务", "paths": ["app/order/**"], "status": "proposed" }] }`。`version` 只认 1；AI 只写 `proposed`。

[跟着开发走]
    文档不是开发完再补的东西。装了框架的项目，下面每一步各有人带着它，本 skill 只在头两步出面：
    - 起头：需求规格生成之后（或 dev-builder 开工时），没有 docs/readable-src/config.json 就跑 `init` 与 `build`——人读版需求规格当场就有；数据库设计与架构设计等建表文件、代码出现了、配置跟上了，自己长出来。这一步不提分组、不写说明。用户明说不出的不建，记进 progress.md 的 Pinned——之后谁开工都先看这一条，不再起头
    - 配置跟上项目：配置是起草那一刻的项目。`init --suggest` 报之后新出现而没列进去的建表文件、代码目录、需求规格与架构文档；提交前检查也会顺带提醒，看到就填进 config.json。它报的不是都要填：用户有意不出的那一份（不出人读版需求规格、不挂旧架构文档）不填，把那个文件写进 `ignore`；确实不想进文档的目录同样写进 `ignore`，就不再报
    - 每个 Task：改的人带着文档一起交（dev-builder SKILL.md [开发规则清单] 的 [人读文档]）——新加、改到的表、列、模块的说明当场写，新表、新文件在 map.json 里就近归位
    - 每次提交：pre-commit-check 自动重出页面，页面有变化没暂存就拦下；放行的那一回把结构与上一个提交比一次，新多出来的循环依赖（新的一组，或已有的一组里文件对数变多）、越层引用、未归属的文件、超过 1000 行的文件当场点名，只提醒不拦
    - 审查：code-review 的 Stage 1 核 `check` 是不是 0 条、新写的说明讲得对不对
    - 每个 Phase 收尾：四步走第二步跑 `check`；这个 Phase 新加的表与文件归位，过期的导读重写。从头跟着开发长起来的项目，表过了十来张还没分组、代码平铺而还是「按目录分的」时，在这一步提一份分组与模块划分（`proposed`）；已经写了一大半才起头的项目，存量不在这一步补
    - 发版之前：主 Agent 核 `check` 报「不一致 0 条」
    - 随时：`node .claude/scripts/project-status.mjs` 的「人读文档」一行报现在到哪；框架升级之后 `doctor.sh` 提示页面要不要重出
    这条线上谁都不用把存量一次写完：没写的说明只报数、不算不一致。存量要补齐，走 [第一次]。

[第一次]
    命令都是 `node .claude/scripts/readable-docs.mjs <子命令>`，在项目根跑。存量项目一次补齐时五步都走；跟着开发走的项目，起头只做第一、二步。
    第一步：`init`，然后打开 config.json 核两样——`ddl` 按执行顺序列全，有的表只在代码里建，把那个代码文件也列进来；`codeRoots` 把所有会碰数据库的代码目录列全，漏一个目录，页面上就有一批表显示「没有找到写这张表的代码」。`spec` 指向需求规格（根目录有 Product-Spec.md 时 `init` 自己填上），不出这一份就写 null，并把它的文件名写进 `ignore`（不写的话 `init --suggest` 每次都报它漏了）；`archDocs` 列项目原有的架构文档与决策记录（一份一份列路径，只认 Markdown），没有就是空数组。代码根目录下不入库的产物（构建输出、本地数据）在 `ignore` 里排掉——页面是入库的生成物，跟着它们变的话换一个副本 `check` 就报对不上。
    第二步：`build`，读它的报数行：未解析的语句、没扫成的文件、代码里建的表各有多少，不是 0 的逐项看首页的清单，该改配置的改配置。
    第三步：提一份业务分组写进 map.json 的 `tableGroups`，`status` 一律写 `proposed`。读每张表的来源注释与写它的代码，按业务里的哪件事分，不按表名前缀分；组的先后就是页面上的阅读顺序。再看首页「表名是运行时拼的」清单，能从代码里确定全集的写进 `dynamicTables`，确定不了的不写。
    第四步：写说明（见 [写说明]），先出小样——挑一个分组（三到五张表）把表与列写齐，连同整库与这一组的导读，`build` 后请用户看这几页：详略、口吻、业务讲到哪一层对不对。用户点头了再照同样的写法铺开，不点头的先改小样；一口气铺完再给人看，返工的是几百段。铺完 `build`，亲眼看页面——至少首页、一个分组页、一张表页，配了需求规格的再看它的清单页与条目最多的那一章，出了架构设计的再看架构首页、文件最多的那个模块页与接口总表。看的办法：`node .claude/scripts/page-shots.mjs docs/readable index.html <别的页…>`，它用本机已有的 Chrome / Chromium / Edge 把每一页切成一段一段的图（默认落在 .claude/evidence/page-shots/，不用另装东西），一张一张读——说明落在该在的位置没有、图画出来没有、表排不排得开；它报「横向溢出：有」的页找出是哪一块撑宽了。它退出码 3（看页面缺席）就明说没看过，不冒充看过；怎么读它的输出见 references/reading-the-numbers.md。
    第五步：`check`，报「不一致 0 条」才算完。

[写说明]
    `pending --json` 给出还缺什么，每张表附一份上下文。量大时按分组分批，一批一个 fresh 的 Sub-Agent，派单里写明：先读需求规格里讲业务的段落、再读写这张表的代码，然后下笔。说明写进一个文件，每段以 `## <锚点>` 开头（`table:<表>`、`column:<表>.<列>`、`group:<组 id>`、`doc:db`，架构的是 `module:<模块 id>`、`doc:arch`），交 `note put --file <文件>`；有一段不合格整批不落盘，照它报的原因改了重交。派单怎么写、交回来要带什么、主 Agent 收回来之后核什么，见 references/dispatch-templates.md；详略与口吻照 references/sample-notes.md。
    规矩：
    - 读者懂数据库与编程、不懂这门业务：先讲业务再讲技术，行话第一次出现时解释半句
    - 表的说明第一段只写一句话——存的是什么、一行代表什么，不超过 60 个字；后面按需要写：什么时候被哪一步写进来、之后谁改、连着哪几张表看、最容易看错的地方
    - 列的说明一到两句，写名字和类型看不出来的；每个列都写
    - 组的说明三到五句；`doc:db` 讲整库的主线：数据从哪来、中间做了什么、给谁用
    - 每句话都指得到出处；拿不准的写「待确认：……」，不编
    - 不写开发史；例子一律合成，不带真实数据；不出现内网地址、账号、密钥
    - 正文是普通文字：空行分段、`- ` 开头是列表、反引号里是等宽字，别的排版不用
    - 认真写，不因为量大就应付：一个任务改了很多表或模块，对应的说明就一段一段照现在的代码重写——读了再落笔，不批量套话，不把名字翻译一遍交差。这份力气值得花，没参与的人读得懂这个系统靠的就是它
    - 写不顺是信号：一句话说不清一张表存的是什么、一个模块管什么，或者得用「以及」「另外还管」把几件不相干的事并列才写得全——多半不是说明难写，是表或模块没分好。属于项目判断的（业务分组、模块划分）回头改 map.json，分顺了再写——调划分是因为原来分错了，不是为了让数好看，不为了消掉循环依赖、越层引用把不相干的文件凑到一起；代码或表结构本身该拆的，不在说明里替它圆，单列出来交给用户
    写的时候发现代码与注释、需求规格对不上的地方，单列出来交给用户，不悄悄按其中一边写。

[人读版需求规格]
    这一份只把需求规格换一种排法：一个字不加、一个字不少，没有 AI 写的说明，也不为了页面好看去改规格的写法。图只从来源已有的结构画（章节地图、有序步骤、用箭头写的流程链），`build` 的报数行多一行：几章、几块、隐去了几处。
    - 规格改了之后重新 `build` 就跟上了，没有要补写的东西；`check` 报的若是需求规格那一项（缺块、多块、字不同、挂的位置或级数不同、图里的字对不上），多半是有人手改了页面——重出，不去改页面
    - `build` 退出码 3 并点名规格的某一行对不上：那是切块丢了字被自检拦下，是生成器的缺陷不是规格的错——把那一行的写法记成 feedback 回流框架，不为了过自检去改规格的内容
    - 清单页顶上的隐去清单逐行看一眼：来源里有内网地址、口令这件事本身要告诉用户；规则认不出内网域名、账号名、人名，交出去之前提醒用户把页面过一遍
    - 条目带编号（`[REQ-…]`）的，页面上这一条的地址就是编号，别处增删不影响；没有编号的按章节路径与开头的粗体词定地址，改了这两样地址就变——有人要长期引用某一条时，建议给它编号

[架构设计]
    配了 `codeRoots` 就出这一份：文件、文件之间的引用、接口、每个模块读写的表从代码里机械取；文件怎么归成模块是项目判断（map.json 的 `modules` 与 `layers`），每个模块管什么是说明（`module:<模块 id>`），整个系统怎么读是导读（`doc:arch`）。页面上三样分开标，不混。
    - 没写 `modules` 时按目录分，页面上标着「按目录分的」；平铺的目录这样只分得出一个大模块，要提一份划分。提的办法：三样线索互相印证——接口路径的前缀、读写的表属于哪个业务分组、文件头说明里讲的事，文件名的前缀只是辅助；一个模块对应业务里的一件事，公共的支撑代码单独成模块；提完先给每个模块试写那一句话的职责，写不出、或者要并列几件不相干的事才写得全的，回头重分，分顺了再铺说明；`paths` 用通配、先到先得，`status` 一律写 `proposed`。写完 `build`，报数行里「未归属的文件」「项目判断里对不上的」都到 0 才算提完。文件多时派一个 Sub-Agent 专门提，派单见 references/dispatch-templates.md 第二份
    - 项目自己有架构文档或模块登记的，先读它；提议与它不同的地方（分得更细、层的叫法不一样）向用户说清，由用户定用哪一套。它们写进 `archDocs`，页面上逐块照排、顶上标明是旧文档，不摘录、不改写
    - 模块说明量大时按层或按业务分批，一批一个 fresh 的 Sub-Agent：`pending --json` 给每个待写的模块一份上下文，派单里写明先读这个模块各文件的文件头说明与接口、再读需求规格里对应的条目，然后下笔。第一段只写一句话——这个模块管什么（清单页拿它当这一行）；后面按需要写：不管什么、一次典型的调用从哪进到哪出、改它要小心什么。`doc:arch` 等模块说明都落盘之后再写
    - 说明里不描述页面当下的样子（「入口一栏是空的」「被列进某张清单」）——页面跟着代码与生成器变，这种话过期了指纹也看不出来
    - 首页「结构上看得出的」（循环依赖、越层引用、超过 1000 行的文件、没有被别的文件引用的）是照引用关系算出来的事实，算不算问题由人判断，不替用户下「这是债务」的结论
    - 「没解析到的引用」「运行时才定的引用」不是 0 时去首页看清单：里面每一条都是生成器明说拿不准的地方，写说明时别把它们当成已经连上的依赖。接口的完整路径拼不出的，页面上照原因标着，不给猜的地址
    - 说明绑的是模块的文件清单、接口与它依赖的模块：加了文件、多了接口、多依赖了一个模块才标「待更新」，只改函数体不标
    - 用源码的副本写说明时，副本要与真实仓同样齐全；副本里缺的文件（设计文档、接口约定、部署配置）不写成「待确认」了事，回到真实仓里查实了再落笔

[来源变了之后]
    边开发边写，不攒到开发完再补：碰了建表定义或读写表的代码、给一个模块加了文件、接口或跨模块引用的 Task，说明由改代码的那一位当场补齐，验收看 `check`（见 dev-builder SKILL.md [开发规则清单] 的 [人读文档]）；页面不用人记着重出，pre-commit-check 在每次提交前自动重出一遍，有变化会拦下来让你 `git add docs/readable` 后重提。
    改了建表定义、会碰数据库的代码、map.json 或说明之后：`build` → `pending`（过期的说明会带着旧正文列出来）→ 照新的来源重写后 `note put` → `build` → `check` 报 0 条。表被删了，它的说明成了孤儿：改挂到新的锚点，或者 `note drop`。
    框架升级之后生成器可能变了页面的写法：`doctor.sh` 提示「人读文档与来源或当前生成器不同步」就 `build` 后提交，不留到发版。它提示有说明待更新的——升级改了说明绑定的来源时会出现，比如整库导读从 2026-11-24 起连表名一起绑，写过导读的项目升级后必然待更新一次——在升级那一轮由主 Agent 照现在的来源重写，不留给下一个开发 Task 去背。
    项目的每个开发副本都要装着带生成器的框架：从没装的副本提交的改动不会带着重出页面，文档就落下一截而没人知道——`check` 是兜底，发版之前必看。
    几个副本要升级就一起升：生成器版本不一样的两个副本，会在各自提交时把页面改回自己那一版的写法。顺序是先给每个副本装上新框架，再在一份没有人用的工作副本里（`git worktree add <目录> <远端分支>`，生成器用 `--root` 指过去）重出、把待更新的说明重写、`check` 到 0 条，提交推送，各副本再快进拉取——不在别人正开着会话的工作树里重出。
    页面是生成物，合并时不手工合：合并、变基、拉取之后跑一次 `build`——它整页重写，冲突标记随之消失；没报冲突的页面也可能被合错（两边各给一张表加一列，自动合并出来的页面 `check` 报过 7 条）。说明文件冲突了先任取一边（`git checkout --ours <文件>`），再把合好的正文经 `note put` 落盘，指纹由它重盖；然后 `build`、`check`，页面有变化就 `git add docs/readable` 一起提交。
    交出去之前由用户或他指定的人抽审，`note confirm <锚点…> --by <名字>`。AI 不替人 confirm，也不往 map.json 里写 `confirmed`。

[交给用户]
    出完、补完一份文档，交代四样，分开说：
    - 取自来源的：几张表、几个模块、几个接口；生成器明说读不出的各有多少（未解析的语句、没解析到的引用、运行时才定的引用）
    - AI 提议、等人确认的：业务分组与模块划分——几组、几个模块、哪几处拿不准，与项目自己的架构文档哪里不一样
    - AI 写的草稿、等人抽审的：说明一共几段，其中「待确认」几处、各是什么。能在真实仓里查实的先查实，查不实的才列给用户
    - 写的过程中发现的：代码与注释、需求规格对不上的地方，看着没人用的表、列、文件——并成一份单独交，注明未经人核实；不悄悄按一边写，也不替用户判是不是缺陷
    然后是等用户定的事（分组与模块划分认不认、谁来抽审、隐去清单里有没有要处理的），和怎么看：浏览器直接打开 docs/readable/index.html。
