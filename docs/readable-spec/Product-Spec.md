# Product Spec — 人读文档（给接手的人看的工程文档集）

> 版本 v1.0，2026-11-22。本仓是框架仓，这份规格描述的是框架要新增的一项能力，所以放在 docs/readable-spec/，不放仓库根。
> 标记：`[确认]` 用户确认的事实；`[推断]` AI 的推断；`[默认]` AI 采用的低风险默认，用户可否决；没定下来的只住在文末那张问题表里。

## 0. AI 使用说明
- 本文档是「人读文档」这项能力的范围、行为与验收的事实来源；dev-planner / implementer / code-reviewer / tester 按它开工。
- 优先实现 P0；「非目标」里排除的不做；按「成功判据」与功能条目的产出判断完成。
- 标 `[推断]` `[默认]` 的条目，实现时若现场证据相反，回报「需求存疑」并附反例，不自行改需求。

## 产品概述
- 这是什么：给 AI 写出来的项目配一套人读得懂、跟得上来源的工程文档——需求规格、数据库设计、架构、数据结构与算法设计、测试设计等——让没有 AI 编程工具的团队能接手。`[确认]`
- 为什么现在做：digifiber-conflation 约两周后启动交接。接手团队约 10 人（1 个架构师 / SE、6 个开发、3 个测试），没有 Claude，只有千问、豆包；他们说 AI 写的代码看不懂——没有数据结构设计、没有数据库设计、没有算法设计。`[确认]`（来源：案例 1）
- 谁受益：接手团队（能下手）；用户（交得出去）；审核的客户（有东西可审）。谁买单：用户——来源每改一次，文档要跟着刷新，花时间与 token。谁可能变差：AI 这边的开发节奏多一步同步。`[推断]`（依据：同步是硬约束，必有成本）
- 核心价值：接手的人不问原作者，也知道从哪下手。`[确认]`（来源：用户「现在没人接得住」「无从下手」）
- 风险档位：对外（客户会审核）。`[确认]`（来源：用户「开发看，客户也会审核」）

## 应用场景：工作现状故事

**案例 1：digifiber-conflation 交不出去**（来源：用户口述 2026-11-22；接手团队的话是转述）
接手团队拿到仓库后的路数是：先看数据库设计，再看架构，再看软件设计，然后自己手写代码往里加。现在这个仓里：Product-Spec.md 424KB、DEV-PLAN.md 643KB，没有 README；建表定义文件里 77 张表、另有两张是代码里直接建的（2026-11-23 本机副本实数），没有数据库设计文档；架构文档写在 8 月的 v2.39，之后需求改到 11 月 19 日，它没跟；算法设计只有「传统段还原」一个模块有。Product-Spec.md 他们看不懂——它是写给 AI 记录用的。

**例外**：接手的人如果用得上能读代码的 AI（哪怕 Codex、Grok），交接本来不难。这套文档是给只有人、加上只能聊天的 AI 的团队准备的。（来源：用户「如果大家都用AI，还是很简单的」）

## 功能需求

**核心功能**
- [REQ-DOC-001] 数据库设计：维护者跑一条命令 → 系统从项目里现行的建表定义读出每张表 → 得到一份数据库设计文档 `[确认]`（来源：案例 1）
  - 每张表有：一句话用途、每个字段的名字 / 类型 / 约束 / 含义、与别的表的关系、谁写它谁读它（到模块与文件）、它服务的需求 `[默认]`（依据：SC-1 的三问）
  - 表与表的关系有图，一张图只画一组相关的表 `[默认]`（依据：用户此前定过「一张图只画一件事」）
- [REQ-DOC-002] 架构设计：维护者跑一条命令 → 系统从代码的模块划分与依赖关系、加上现有的架构文档与决策记录读出现状 → 得到一份架构文档：分层与模块图、每个模块的职责 / 对外接口 / 依赖、关键决策与被拒的方案、已知的债务 `[确认]`（来源：案例 1）
- [REQ-DOC-003] 数据结构与算法设计：对每个有业务规则的模块 → 系统从代码与已有的设计详述读出 → 得到该模块的设计文档：核心数据结构（字段含义、从哪来到哪去）、算法规则逐条（判据、先后顺序、例外、常量、一个例子、代码位置、守着它的测试）、主流程图 `[确认]`（来源：用户转述「没有数据结构设计……没有算法设计」）
- [REQ-DOC-004] 人读版需求规格：Product-Spec.md 的每一条 → 系统逐条投影 → 得到一份排好版、带图的需求规格，条目一一对应，内容一个字不少 `[确认]`（来源：用户「1:1 对应」「不能有丢失」）
  - 能从结构直接画出来的图由系统画：章节地图、有序步骤的步骤图、用箭头写的流程链；范围、权限、判据这些段本来就是表，照表格显示 `[默认]`（依据：图只从来源已有的结构画，不加一个字）
- [REQ-DOC-005] 关联：读者从一条需求、一张表、一个模块、一条算法规则任一处出发 → 系统给出它连着的其它几样 → 得到「谁实现它、数据存哪、怎么验」；连不上的明示「未关联」，不留空白 `[确认]`（来源：用户「还要关联」；SC-2）
- [REQ-DOC-006] 同步：来源（Product-Spec.md、代码、库结构）改了 → 系统重新生成受影响的文档 → 读者看到的永远对应现行来源 `[确认]`（来源：用户「及时同步」「指不定其实人在看」）
  - 机械取出的内容（表结构、条目原文、关联）随来源直接更新 `[默认]`
  - 需要 AI 写的说明与另画的示意图，绑定它所依据的那段来源的内容指纹；来源变了而说明没重写的，页面上自动标「待更新」，不冒充现行 `[默认]`（依据：业内「可疑链接」的做法）
  - 文档跟着开发过程自动走，不靠谁记着说一句「出文档」：需求规格一生成就出人读版；开发的每一步——计划、派单、编码、审查、收尾、发版——各带着文档的那一份；项目的状态里报得出文档到哪了；框架升级后提醒重出 `[确认]`（来源：用户 2026-11-24「你是让后续的，Agent开发过程能正常，自动生成这些文档」）
  - 装了框架的项目默认出人读文档，用户明说不出的才不建 `[确认]`（来源：用户 2026-11-24「认，默认出人读文档」；此前是主 Agent 定的默认）
  - 存量项目一次补齐（提分组、提模块划分、写存量的说明）只在用户要时做；开发任务只对这次新加、改到的表、列、模块负责 `[默认]`（依据：存量补齐量大、要先给人看小样，塞不进一个开发任务）
- [REQ-DOC-007] 核对：维护者跑一条命令 → 系统逐项比对文档与来源 → 得到一份不一致清单：需求条目缺失或内容不符、表或字段缺失、说明已过期、关联指向不存在的东西；清单为空才算同步 `[确认]`（来源：用户「100% 契合」）
- [REQ-DOC-008] 测试设计：系统从测试代码读出 → 得到测试文档：测试分几层、各怎么跑、每条需求与每条算法规则由哪些测试守着、哪些没有测试 `[推断]`（依据：团队里 3 个测试；用户列了「测试设计」）

**辅助功能**
- [REQ-DOC-009] 上手指南：读者照着做 → 装好环境、把项目跑起来、把测试跑通、完成一次示范性的小改动 `[默认]`（依据：SC-3；conflation 现在没有 README）
- [REQ-DOC-010] 业务入门与术语：读者先读它 → 系统把这门业务讲给他 → 知道这里的东西叫什么、规则按什么算 `[确认]`（来源：用户「他们必须懂业务知识」「对，要讲业务」；内容取自 Spec 的规则与例外和项目的 domain/ 口径库）
- [REQ-DOC-011] 小份自成一体：读者把某一份文档整段贴给聊天式的 AI 提问 → 系统给出的每份文档按模块切开、不依赖别的文件就读得通 → 得到单份就问得动的材料 `[确认]`（来源：用户「我认你的建议」）

## 规则与例外
| 规则 | 例子 | 例外 | 来源 |
|------|------|------|------|
| 这是框架能力，不是一次性产物：每份文档都由框架里可重复跑的生成器产出，装了框架的项目都能用 | conflation 的数据库设计小样是跑生成器出来的，不是手写一份 | 无 | `[确认]` 用户「这个东西，是框架能力，不是你搞一下次就完了」 |
| 文档只由来源生成，不手改 | 有人直接改了数据库设计文档里某个字段的说明，下次生成会被覆盖 | 交接之后接手方手改，不再保证同步（OUT-1） | `[确认]` 用户「只能从 Product-Spec.md 生成，被它刷新」 |
| 需求规格这一份只认 Product-Spec.md | 人读版里不出现 Spec 里没有的需求 | 无 | `[确认]` 同上 |
| 数据库、架构、数据结构与算法设计以现行代码为准 | 架构文档写的是 v2.39，代码已到 v2.62，以代码为准重出 | 代码里看不出的设计意图（为什么这么分层），取自现有的架构文档与决策记录，并标明出处与日期 | `[确认]` 用户「对」 |
| 事实与解释分开 | 字段类型是从建表定义取的事实；「这个字段记录的是光缆的 A 端」是 AI 写的解释，两者在页面上看得出区别 | 无 | `[默认]` 依据：框架既有的「四种话分开说」 |
| Spec 不为文档让路 | 人读版缺一张图，不往 Spec 里加图的定义 | 无 | `[确认]` 用户：Spec 优先级高于文档 |
| 例子不带真实数据 | 文档里举的表记录、坐标、小区名一律是合成的 | 无 | `[推断]` 依据：conflation 的合规红线——真实设计与运营商数据仅内网 |
| AI 写的说明认真写；写不顺回头看划分 | 一个任务改了十几张表，说明就一段一段照现在的代码重写；一个模块的职责一句话说不清，先回头调划分再写 | 代码或表结构本身该拆而这一轮动不了的，不在说明里替它圆，单列出来交给用户 | `[确认]` 用户 2026-11-24「那是非常值得，而且一定要认真写，这也促使，你去更好划分模块，避免文档难写」 |
| 文档即代码：文档照出代码的结构，不替它遮丑 | 模块之间绕成环、有文件哪个模块都放不进、一张表谁都在写，页面上照实列出来；开发任务交回时这几个数比派单前多了，修掉或写明原因 | 无 | `[确认]` 用户 2026-11-24「文档既代码，文档乱说明代码乱，说明设计不合理，说明架构在腐化，一切都暴露在阳光下，无处躲藏」「文档结构化以后，你要思考的东西更多」 |

## 关键流程

**FLOW-1：交接第一周**（关联：SCOPE-1～5、8）
1. 架构师老周拉下仓库，打开文档首页，先读业务入门。
2. 他进数据库设计，按业务分组看表，点开一张表：用途、字段、关系图、谁写谁读。
3. 他进架构设计，看模块图，点进一个模块，看到它的职责、接口、依赖和它用到的表。
4. 开发小李领到「给某张表加一个字段」的活，从那张表的页面找到写它的模块与文件，再进那个模块的设计文档看相关规则。
5. 测试小陈从测试设计里查到守着这条规则的测试，照上手指南把它跑起来。
6. **高潮**：小李改完代码、测试跑通，全程没有找过原作者。
**失败路径**：某个模块的算法说明标着「待更新」→ 读者看到的是「这段说明写于来源的旧版本，机械部分仍是现行的」→ 他先看代码位置与测试，同时把这一条报给维护者 → 机械取出的部分不受影响，不丢信息。

**FLOW-2：AI 侧改了来源之后**（关联：SCOPE-6）
1. AI 改了一条需求和两张表的结构。
2. 系统重新生成：人读版需求规格里那一条换成新文；两张表的字段表更新；这两张表原有的 AI 说明被标「待更新」。
3. AI 重写那两段说明，标记消失。
4. 核对命令报「不一致 0 条」，这次改动才算完。
**失败路径**：生成中途出错 → 已有的文档保持上一版不动，不留半成品 → 报出错在哪一份 → 修好重跑。

|------|----------|----------------------|--------|-------------|------|
| 来源（Product-Spec.md、代码、库结构、现有设计文档） | — | AI 与用户（照旧） | 生成器只读 | 不动 | `[确认]` |

## 决策依据
| 决定 | 备选 | 为什么 | 谁定的 |
|------|------|--------|--------|
| 需求规格只从 Product-Spec.md 单向生成 | 人读版可手改再回写 | 两份都能改迟早对不上；Spec 是 AI 跟得上项目的依据 | 用户 |
| 设计类文档以现行代码为准生成 | 只从 Spec 生成 | 表结构、模块、算法的真相在代码里，Spec 里没有 | 用户（「对」） |
| 不做反向同步 | 跟踪接手方的手工改动 | 交出去之后不归我们管 | 用户 |
| 文档结构自定，不套模板 | 等一份模板 | 没有模板 | AI 决定（用户委托） |
| 人读版是逐条投影，不是摘要 | 分三层、每条只留现行规则加一个例子 | 摘要会丢内容；用户要求一一对应、零丢失 | 用户（否掉了 AI 先提的摘要方案） |
| 按模块切小份 | 一份大文档 | 人好读，也能贴给聊天式 AI | AI 建议、用户采纳 |
