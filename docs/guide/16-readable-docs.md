# 16 人读文档：给接手的人看的工程文档

这章解决一个问题：**AI 写出来的项目，交给没有 AI 的人接手时没人看得懂**——Product-Spec.md 是写给 AI 记录用的，代码里没有数据库设计、没有「这张表是干什么的」。框架里有一条命令，从项目的建表定义和代码里把事实取出来，生成一套浏览器直接能开的网页；AI 只负责写机器取不出来的那部分（表的用途、字段的含义、这一组表在业务里讲的是哪件事），并且这些话一旦过期会被自动标出来。读完你能：

- 给一个项目出第一份数据库设计文档，知道页面上每一块是从哪来的；
- 把 Product-Spec.md 出成一份人读得下去的需求规格，知道凭什么说它「一个字不少」；
- 出一份架构设计：系统由哪几个模块组成、谁依赖谁、每个模块有哪些接口、碰哪些表，知道哪些是机械取的、哪些是人和 AI 定的；
- 让 AI 把表的用途和字段含义写进去，知道为什么只能经命令落盘；
- 改了建表定义或代码之后，知道哪些说明过期了、怎么刷新、怎么确认文档与来源一致；
- 看懂「项目判断」是什么、页面上的「AI 提议」「人已确认」是什么意思；
- 遇到「没有找到写这张表的代码」「未合并的动态定义」这类提示时知道先查什么。

前置：项目里装了框架，有建表定义（`.sql` 文件，PostgreSQL 方言），本机有 node。读者那一头什么都不用装。现在做完的是数据库设计、人读版需求规格、架构设计三份；算法设计、测试设计在后面几期。架构设计要代码是 Python 或 JS 一族才取得出东西，接口只认装饰器写法的路由。

## 入门：出第一份数据库设计

### 三条命令

在项目根目录下：

```bash
node .claude/scripts/readable-docs.mjs init     # 起草配置，只在第一次跑
node .claude/scripts/readable-docs.mjs build    # 取事实、出页面
node .claude/scripts/readable-docs.mjs check    # 核对页面与来源，「不一致 0 条」才算同步
```

`init` 会在 `docs/readable-src/config.json` 里写下它找到的建表文件和代码目录，**打开看一眼再往下走**：

```json
{
  "version": 1,
  "title": "项目名",
  "ddl": ["app/db/schema.sql"],
  "codeRoots": ["app/api", "app/tools", "web/src"],
  "spec": "Product-Spec.md",
  "ignore": ["**/tests/**", "**/node_modules/**"]
}
```

- `ddl` 按执行顺序列建表文件，后面的能改前面建的表。有的表只在代码里建（程序启动时 `CREATE TABLE IF NOT EXISTS`），把那个代码文件也列进来，否则文档里就少这几张表——`build` 之后首页的「代码里建的表」清单会提醒你。
- `codeRoots` 要把**所有会碰数据库的代码目录**列全。漏一个目录的后果是一批表显示「没有找到写这张表的代码」。
- `spec` 是需求规格的路径，写了就多出一份人读版需求规格（见下面「人读版需求规格」一节）；写 null 就不出。写了路径而文件不在，按配置错报出来，不会悄悄不出。
- `archDocs`（可以不写）列项目原有的架构文档与决策记录，一份一份写路径，只认 Markdown。写了就在架构设计下面多出这些文档的网页版（见「架构设计」一节末尾）。根目录有 `Architecture-Design.md` 时 `init` 会自己填上它。

`build` 之后用浏览器打开 `docs/readable/index.html`。页面是静态的，不联网、不带脚本，可以整个目录拷走，也可以打印。这个目录随项目入库，接手的人拉下仓库就能看；**不要手改它**，下次生成会覆盖。

AI 出完文档自己也要看一遍页面，不拿「核对 0 条」当看过：`node .claude/scripts/page-shots.mjs docs/readable index.html db/index.html` 用本机已有的 Chrome / Chromium / Edge 把点名的页面切成一段一段的图给它读，不用另装东西。本机没有浏览器时它退出码 3、明说「看页面缺席」，AI 会如实告诉你页面没看过。

### 页面上有什么

| 页面 | 内容 |
|---|---|
| 数据库首页 | 整库的说明、分组关系图、分组清单（每张表一句话用途）、视图与数据库函数、几张「读不出的」清单 |
| 分组页 | 这一组的说明、组内的关系图、组内各表的摘要 |
| 表页 | 说明 → 来源里的注释 → 以它为中心的关系图 → 字段（类型、可空、默认、键与约束、引用、含义）→ 谁在写、谁在读 → 表级约束 → 索引 → 建表之后的改动 |

每一块内容都标着来历，共四种：

| 标记 | 意思 |
|---|---|
| 取自来源 | 从建表定义或代码里机械取出来的事实 |
| 来源里的注释 | 建表文件里的 `--` 注释与 `COMMENT ON`，原样照搬 |
| 说明 · 草稿 / 已抽审 | AI 写的解释；抽审过的带着谁、哪天 |
| 项目判断 · AI 提议 / 人已确认 | 机器推不出、由人或 AI 定的归属（怎么分组、运行时拼的表名归到哪张表） |

事实和解释在页面上分得开，是这套东西的底线：字段类型是取来的，「这个字段记的是什么」是写的，读者要能一眼看出该信几分。

### 读不出的会明说

建表定义里有些东西静态读不出来，页面不装作读出来了：

- **未合并的动态定义**：`DO $$ … $$` 块里在运行时才改表结构的语句。被它点到的表，页面顶上有一条提示「下面的约束可能与库里不一致」。
- **表名是运行时拼的**：`f"DELETE FROM {table} WHERE …"` 这类，认不出是哪张表。
- **未命名**：没写名字的约束。库里它其实有个自动生成的名字，但静态算不准，写出来就是把推断当事实。

### 人读版需求规格

Product-Spec.md 是写给 AI 记录用的：一条需求几千字不分段，开头压着近百行版本注记，人读不下去。配置里写了 `spec` 之后，`build` 会把它**换一种排法**出成网页，放在 `docs/readable/spec/`——一个二级标题一页，另有一张清单页带章节地图。

它和数据库设计那一份有一处根本的不同：**一个字不加、一个字不少，没有 AI 写的说明**。页面上做的只有排版：

| 排法 | 做了什么 |
|---|---|
| 小标题 | 列表项开头是粗体词的，粗体词当作这一条的小标题 |
| 分句 | 超过 200 个字的条目、段落、引用里的行，在句号、分号、问号、感叹号之后断行，一句一行；括号、引号、等宽里面的不断，`v2.31` 这种紧贴着字的点不算句号 |
| 引用 | 收进可展开的区，标题写「引用（N 行）」加它的第一行；打印时展开 |
| 步骤图 | 同一层连着三步以上的有序列表，前面加一张图，一个方框一步；列表本身照旧完整显示 |
| 流程链图 | 一句话用「→」连着三段以上、每段不超过 30 个字时，在这句话后面画一条链，一个方框一段；带箭头的长叙述不画，已经画进步骤图的那几步也不再画 |
| 本章条目 | 一章里顶层条目有 5 条以上以粗体词开头时，本章目录里把这些词列出来，点了跳到那一条 |
| 序号 | 有序列表显示原文写的序号，不用浏览器自动编的号——原文三条都写 `1.`，页面上就是三个 `1.` |
| 表格 | 显示成表格；宽表在自己的框里横向滚 |

图只从来源已有的结构画，方框里的字都取自它所画的那几条，一个字不编——核对时会把图里的字拿回来源去对。规格写得越有结构（编号的步骤、用箭头写的流程、粗体词开头的条目），页面上的图和索引就越多；一大段不分点的散文，页面上也只能是一段分了句的散文。

每页顶上写着「本页内容逐块取自哪个文件的第几行到第几行」，读者拿着行号能回到来源。

**引用某一条**：鼠标移到一条上，它的左边会出现一个「#」记号，点它，地址栏里就是这一条的地址（`spec/s-04.html#REQ-DOC-004` 这种）。条目开头带 `[REQ-…]` 编号的，地址就是编号；没有编号的按「章节路径加开头的粗体词」定地址，别处增删条目不影响它，改了这一条的章节或粗体词才会变。开头既没有编号也没有粗体词的条目，地址按它在本章里的次序定，前面插进一条就会后移——要长期引用的条目，给它编号。章的页面按章的序号命名（第 04 章就是 `s-04.html`），中间插进一章，后面各章的文件名会后移。

改了 Product-Spec.md 之后重新 `build` 就跟上了，没有要人补写的东西；提交前检查会自动重出（见「开发的时候怎么跟」）。**不要改页面去「修」规格**——页面是生成物，规格只在 Product-Spec.md 里改。

### 架构设计

配置里有 `codeRoots` 的项目，`build` 还会出一份架构设计，放在 `docs/readable/arch/`。它回答接手的人第二步要问的话：**这个系统由哪几块组成、每一块管什么、块与块之间谁用谁、每一块对外提供什么、碰哪些表**。

| 页面 | 内容 |
|---|---|
| 架构首页 | 导读 → 总图 → 模块清单（每个模块一句话职责、文件数、规模、接口数、读写几张表、依赖与被依赖几个模块）→ 结构上看得出的 → 读不出的与对不上的 |
| 模块页 | 说明 → 邻居图（它依赖谁、谁依赖它）→ 接口 → 文件与文件头说明全文 → 它依赖的模块（哪几对文件、用了哪些名字）→ 依赖它的模块 → 对外提供的名字 → 读写的表 → 用到的外部包 |
| 接口总表 | 全部 HTTP 接口一张表，按完整路径排，带所属模块 |

数据库设计的表页也跟着多一样：「谁在写」「谁在读」的每个文件后面标着它所属的模块，点了到模块页；模块页的表点了回表页。

这一份里**机械取出来的**有四样，都只读源码的文本、不运行代码：

- 文件：路径、规模、是不是入口，和**文件头说明**——文件开头那段文档串或注释，原文完整照搬。项目里文件头写得越认真，这一页越有用。前端文件常常先写引用、再在组件上方写说明，这种写在引用语句之后的第一块注释也取，页面上标一句「写在引用语句之后的第一块注释」：它说的有时只是紧跟着的那一条定义，由读的人判断。入口认两种：带 `if __name__ == "__main__":` 的文件，和在模块级定义了 `FastAPI(…)` 应用的文件。点开头的目录与 `__pycache__` 不进；别的不入库的产物（构建输出、本地数据）要在配置的 `ignore` 里排掉，不然页面会跟着它们变。
- 引用：谁 `import` 了谁、引了哪些名字。字符串、注释里的不算；解析不到的、运行时才定的各有清单，不悄悄丢。Python 的绝对引用照解释器找模块的先后去对文件：脚本所在的目录、引用方自己的代码根、别的代码根、项目根；代码根本身是个包时（有 `__init__.py` 并且有人按包的写法引用它），包里的 `import logging` 指的是标准库，不会被接到同目录下同名的文件上。拿不准的（包里与外部包同名的文件、对上了扫的范围之外的文件）进「没解析到的引用」并写明两种读法。
- 接口：只认装饰器写法的路由（FastAPI 这一类），工厂函数造出来的路由器、`mount` 挂上来的子应用也认。完整路径把一路的前缀拼起来；拼不出的不给猜的地址，照原因标「前缀是运行时定的」或「没找到它挂在哪，前面可能还有一段前缀」。长得像接口而认不出路由器的，进「没解析到的引用」，不会哪张清单都不进。
- 读写的表：取自数据库设计那一份的代码扫描。

**机械取不出来的**有两样，页面上标得出是谁定的：

- **文件怎么归成模块**是项目判断，写在 `map.json` 的 `modules` 里（见「项目判断」）。没写时按目录分——平铺的目录这样只能分出一个大模块，页面上会标「按目录分的，还没有项目判断」。
- **每个模块管什么**是 AI 写的说明，锚点 `module:<id>`，整个系统的导读是 `doc:arch`，落盘、过期与抽审的办法和表的说明完全一样。

页面上不写确切的行数，只写规模（文件分四档，模块写「约 5 千行」这样的约数）——不然代码随便加几行，页面就跟着变，每次提交都带一批没有内容的差异。

「结构上看得出的」那几张清单——循环依赖、越层引用、特别大的文件、没有被别的文件引用的文件——都是照引用关系算出来的事实，算不算问题由人判断，页面不替人下结论。

**项目原有的架构文档**：代码里读得出「现在是什么样」，读不出「当初为什么这么定」。项目自己写过架构文档、决策记录的，把路径列进配置的 `archDocs`，`build` 会把每一份照人读版需求规格的办法换排成网页（`arch/doc-01/`、`arch/doc-02/`……），一个字不加、一个字不少，零丢失的核对同样管它们；架构首页开头有一句指过去，末尾有一张清单。每一页顶上都有一条横条写明「这是某某文件的原文，写的时候对应的代码以它自己标的版本为准；现行的结构以架构首页为准」——它们是旧文档，不是从现在的代码里取的事实，两样在页面上分得开。

## 进阶：说明、过期与核对

### 让 AI 写说明

机器取不出「这张表是干什么的」。看还缺什么：

```bash
node .claude/scripts/readable-docs.mjs pending          # 人看的清单
node .claude/scripts/readable-docs.mjs pending --json   # 给 AI 的：每张表附一份 4KB 以内的上下文
```

AI 照上下文和代码写，一个文件里放若干段，每段以 `## <锚点>` 开头：

```
## table:orders
一行是一张订单，下单时由结算接口写入。

付款成功后状态改成已付；退款不删这一行，另记在 `refunds`。

## column:orders.status
订单状态：`pending` 待付款、`paid` 已付、`closed` 超时关闭。
```

锚点六种：`table:<表>`、`column:<表>.<列>`、`group:<组 id>`、`doc:db`（整库的说明），架构设计那一份另有 `module:<模块 id>` 与 `doc:arch`（整个系统的导读）。然后交给命令落盘：

```bash
node .claude/scripts/readable-docs.mjs note put --file notes.md
```

**说明只能经这条命令落盘**，不要直接编辑 `docs/readable-src/notes/`。命令会逐段校验（锚点存在、正文不空、没有内网地址与密钥样式的字样），有一段不过整批不落盘；通过的由命令按当时的来源盖上指纹。指纹不由写的人给——否则过期的说明照抄一个新指纹就能冒充现行。

写说明的几条规矩（框架的 readable-docs skill 里有全文）：

- 表的说明第一段只写一句话：这张表存的是什么、一行代表什么。清单页拿它当这张表的那一行。
- 先讲业务再讲技术；每句话都要在代码、注释、需求规格里指得到出处，拿不准的写「待确认：……」。
- 例子一律合成，不带真实的客户数据。
- 不写开发史，页面上另有「建表之后的改动」放原文。
- 模块的说明第一段也只写一句话：这个模块管业务里的哪件事，清单页拿它当这一行。后面写它管到哪为止（和相邻模块的分工）、一次典型的事从哪进到哪出、它是哪些表的主人、改它要小心什么。文件和接口的清单页面上已经有，不用复述。
- 认真写，量大也不应付：一次改了很多表或模块，对应的说明就一段一段照现在的代码重写。
- 写不顺是信号：一句话说不清一张表存什么、一个模块管什么，多半是没分好，不是说明难写。AI 会先回头调分组或模块划分再写；代码或表结构本身该拆的，它单列出来交给你，不在说明里替它圆。

### 来源变了会怎样

改了建表定义或代码之后重新 `build`：

- 机械取出的部分（字段、关系、谁写谁读）直接跟着变。
- 说明的指纹对不上了，就**原文照显并加一条横条**：「这段说明写于来源的旧版本，机械取出的部分仍是现行的」。它不会被藏起来，也不会看着和现行的一样。

什么改动算「对不上」是按切片算的，不是整张表：

| 说明挂在 | 绑定的来源切片 | 所以 |
|---|---|---|
| 表 | 表名、表注释、各列的名字与类型、主键与外键 | 加一个索引、改一个默认值不过期；加一个列、改一个类型才过期 |
| 列 | 这一列的定义全文与注释 | 改它的默认值、约束会过期 |
| 组 | 组的标题与成员 | 表挪了组才过期 |
| 整库 | 各组的 id、标题与组里的表名 | 加了表、删了表、表挪了组、组的划分变了才过期 |
| 模块 | 模块的 id 与标题、文件清单、接口、它依赖的模块 | 改函数体不过期；加了文件、多了接口、多依赖了一个模块才过期 |
| 架构导读 | 各模块的 id、标题与所在的层 | 模块的划分变了才过期 |

`pending` 会把过期的列出来并带着旧正文，AI 照新的来源重写后再 `note put`，横条消失。表被删了，它的说明成了「孤儿」，不上任何页面，`pending` 会带着正文列出来，方便改挂到新表上，或者 `note drop` 掉。

### 开发的时候怎么跟

边开发边写，不攒到开发完再补。改的人当场写一两句，比事后让人重读代码去猜便宜得多，也准得多。装了框架的项目不用谁记着说一句「出文档」，开发流程里每一步各带着它：

- **起头**：需求规格一生成，主 Agent 就跑 `init` 与 `build`，人读版需求规格当场就有，交付的话里会告诉你给人看的版本在哪。数据库设计与架构设计等建表文件、代码出现了自己长出来。这个项目不想出的，说一声就不建。
- **配置跟上项目**：配置是起草那一刻的项目。后来新出现的建表文件、代码目录没列进去，`readable-docs.mjs init --suggest` 报得出来，提交前检查也会顺带提醒一句；它报的不是都要填：确实不想进文档的目录、有意不出的那一份需求规格或架构文档，写进 `ignore` 就不再报。

- **提交前自动重出**：项目里有 `docs/readable-src/config.json` 时，提交前检查会先把页面重出一遍。页面有变化就拦下这次提交，`git add docs/readable` 之后重提即可；重出自己失败不拦提交，只把原因报出来。
- **任务验收**：任务碰了建表定义、读写表的代码，或者给一个模块加了文件、接口、跨模块的引用，就带着文档一起交——说明由改代码的那一位补齐，`check` 报 0 条才算完成；派单里写着这一条，实现者的回执里带着 `check` 的结果。主 Agent 派单之前先记一次 `check` 与 `pending` 的数：派单前就有的不算这个任务的，验收时缺口不许比派单前多——没写说明不算不一致，只看 `check` 看不出新加的表忘了写说明。没碰这些的改动一个字都不用写。
- **审查**：审查的人多核一项——`check` 是不是 0 条、新写的说明讲的与代码做的对不对得上。
- **阶段收尾**：四步走里多跑一次 `check`；没归到模块的文件、没进分组的表在这一步归位。
- **发版之前**：主 Agent 先核 `check` 报 0 条，交出去的文档要与这一版代码对得上。
- **随时看得见**：`node .claude/scripts/project-status.mjs` 多一行「人读文档」——几页、没写说明的表与模块各几个、过期几段、配置有没有漏项。框架升级之后生成器可能变了页面的写法，`doctor.sh` 会提示「重出后提交」；升级改了说明绑定的来源时（比如整库导读从 2026-11-24 起连表名一起绑），它还会提示有几段说明待更新，升级那一轮照现在的来源重写。
- **项目有几个开发副本**：每个副本都要装着同一版框架——没装的副本提交代码不会带着重出页面；装着旧版的会把页面改回旧的写法。升级时先给每个副本装新框架，再在一份没人用的工作副本里重出、提交、推送，各副本拉取。
- **合并冲突**：`docs/readable/` 下的页面冲突了不用手工合，合并之后跑一次 `build`，它整页重写；说明文件冲突了先任取一边，再让 AI 把合好的正文重新落盘。没报冲突的合并也跑一次 `build`，自动合并出来的页面不一定对。

这条线上谁都不用把存量一次写完：开发任务只对这次新加、改到的负责，没写的说明只报数、不算不一致。项目已经写了一大半才想把存量补齐，是另一条路——说一声「出人读文档」，AI 先出一个分组的小样给你看，点头了再铺开。

为了让页面不跟着无关的改动乱变，**代码文件的行号不上页面**：「谁在写」「谁在读」只写文件、动作和处数。代码一改行号就挪，写上去每次提交都会带一批只是行号变了的页面差异；要找具体位置，拿着文件名到文件里搜表名。建表定义文件（`.sql`）的行号照旧显示；`ddl` 里列的代码文件，它里面那些定义的出处只写文件。各张「读不出来」的清单里，原因那句话同样不带行号。

### 核对：什么时候算同步

```bash
node .claude/scripts/readable-docs.mjs check
```

退出码 0 且末行「不一致 0 条」才算同步。它查四样，配置了需求规格的再加第五样，出了架构设计的再加第六样：

1. **页面是不是现行的**——重新取事实、重出一遍，与磁盘上的逐文件比。改了来源没重出、有人手改了页面，都在这里露出来。
2. **页面上显示的与事实一致**——核对器不信出页面的代码，自己把页面读回来，一个列一个列地和重新取的事实比。出页面的代码要是吞了一个列，第 1 项两边错得一样看不出来，靠这一项。比的是读者看到的字：显示出来的列名、文件路径也在比的范围里，不是只拿藏在页面里的标记配行。
3. **说明**——过期的、孤儿的，各算一条。没写的不算不一致，只报数。
4. **指向不存在的东西**——项目判断里点到不存在的表、页面里的死链接。
5. **需求规格一块不少、一字不差、层次不乱**——把规格重新切成块，再把页面一块一块读回来比。来源里的每一块在页面上恰好出现一次、先后一致、文字相同（有序列表连序号一起比，引用为打印另备的那一份也比），列表的子项挂在原来的父项下面，标题还是原来的级数。报出来的每一条都点到来源的第几行、从第几个字起不同。

6. **架构页面上的与事实一致**——核对器自己把架构那几页读回来，逐段、逐行、逐格与重新取的事实比：首页的模块清单（连同每个模块的文件数、约多少行、接口数、读写几张表、依赖与被依赖几个模块）和下面每一张清单；每个模块页的标题、文件（路径、规模、入口、文件头说明的全文）、接口（方法、路径、处理函数、所在文件、说明的全文）、它依赖的模块、依赖它的模块、对外提供的名字、读写的表、外部包；接口总表的每一条；表页上每个文件标的模块。哪一段整段没出、哪一格显示的字不对、多出一格核对不认识的，都会报。项目判断里对不上的另算一类，要人去改 `map.json`。配了 `archDocs` 的，每一份旧文档照第 5 项的办法逐块核对，报出来的每一条写明是哪一份。

第 5 项报的七种情形：

| 报的是 | 意思 | 多半是 |
|---|---|---|
| 图里的字来源里没有 | 步骤图、流程链图某个方框里的字，在它所画的那几条里找不到 | 手改了图；或出页面的代码有毛病 |
| 页面上没有 | 来源里的一块在页面上找不到 | 有人删了页面里的内容 |
| 不止一处 | 同一块在页面上出现了两次 | 手工复制粘贴过页面 |
| 来源里没有 | 页面上多出一块 | 来源删了一条而没重出 |
| 先后不一致 | 块都在，顺序和来源不同 | 手工挪过页面 |
| 文字不同 | 同一块两边的字对不上；或打印用的那一份对不上 | 手改了页面；或出页面的代码有毛病 |
| 挂的位置或级数不同 | 字都在，子项却不在原来的父项下面，或标题换了级别 | 同上 |

改一次来源的完整来回：`build` → `pending` → 重写过期的说明 → `note put` → `build` → `check` 报 0 条。`build` 自己在落盘之前也会跑第 2 项与第 5 项，不过就不替换，原有页面一个字节不动。

### 抽审

AI 写的说明默认是「草稿」。交接前由人抽着看，看过的记上：

```bash
node .claude/scripts/readable-docs.mjs note confirm table:orders column:orders.status --by 张三
node .claude/scripts/readable-docs.mjs note confirm --all --by 张三     # 只动还是草稿、且没过期的
```

页面上那一段变成「说明 · 已抽审（张三，日期）」。说明被重写之后回到草稿。

### 项目判断

有两类归属机器推不出来，写在 `docs/readable-src/map.json` 里，人和 AI 都可以直接编辑：

```json
{
  "version": 1,
  "tableGroups": [
    { "id": "order", "title": "订单与明细", "tables": ["orders", "order_items"], "status": "proposed" }
  ],
  "dynamicTables": [
    { "file": "app/api/report.py", "reads": ["orders", "refunds"], "writes": [], "status": "proposed" }
  ]
}
```

- `tableGroups`：按业务分组。没有它时按表名前缀分，结果往往是最核心的几张表因为前缀下只有一张，全被甩进「其它」。组的先后就是页面上的阅读顺序。
- `modules` 与 `layers`：把代码文件归成模块、把模块排成层，架构设计那一份用。写法：

  ```json
  {
    "layers": ["界面", "接口", "业务", "数据"],
    "modules": [
      { "id": "ingest", "title": "数据导入", "layer": "业务",
        "paths": ["app/api/import_*.py", "app/api/ingest/**"], "status": "proposed" }
    ]
  }
  ```

  `paths` 是通配（`*` 不跨目录，`**` 跨目录），一个文件归到清单里第一个匹配它的模块，所以窄的写前面、宽的写后面；没有模块匹配的文件进「未归属」，在架构首页单列。`id` 只许小写字母、数字、连字符。模块的先后就是页面上的阅读顺序。标题写短（十来个字以内），它管哪几样东西留给模块说明去讲。
- `dynamicTables`：把一个文件里运行时拼的表名归到具体的表上。只写从代码里能确定全集的（比如来自一个写死的清单）。
- `status` 是 `proposed`（AI 提议）或 `confirmed`（人已确认）。**`confirmed` 只由人改**，AI 只许写 `proposed`。

对不上的地方（组里点到不存在的表、一张表进了两个组；一个文件被两个模块匹配、一个模块的通配一个文件都没匹配到、层名不在 `layers` 里、`id` 写法不对或重复）不会让生成失败，会列在首页的「项目判断里对不上的」，`check` 也会报。

**提模块划分的办法**（平铺的目录最需要它）：三样线索互相印证——接口路径的前缀、读写的表属于哪个业务分组、文件头说明里讲的事；文件名的前缀只是辅助。一个模块对应业务里的一件事，接手的人看标题就知道它管什么；公共的支撑代码（数据库连接、鉴权、配置）单独成模块。写完跑 `build`，看报数行里「未归属的文件」「项目判断里对不上的」是不是 0，再看循环依赖有几组——循环是事实，如实列出来比为了消掉它把不相干的文件硬凑到一起强。

## 精通：它为什么这样做

### 文档即代码

页面是代码结构照出来的样子：每个文件归哪个模块、每个模块一句话管什么、谁依赖谁、哪张表谁在写，都摆在明面上。所以文档乱不是文档的毛病——说明写不顺、模块之间绕成环、有文件哪个模块都放不进，说的是设计不合理、架构在变坏。框架不让文档替代码遮丑：

- 循环依赖、越层引用、未归属的文件照实列在架构首页，算不算问题由人判断，但不会被藏起来。
- 调模块划分只因为原来分错了，不许为了让这几个数好看把不相干的文件凑到一起。
- 开发时先想后写：新加的文件、表，动手之前先定它归哪个模块、哪个分组、一句话管什么。
- 每个开发任务派单前记下这几个数（`node .claude/scripts/readable-docs.mjs structure` 一行报全），交回时多出来的要么修掉、要么写明原因进这一期的结论，不悄悄带过。
- 提交的那一刻机器也比一次：这次提交比上一个提交多出来的循环依赖（新的一组，或已有的一组里又多缠了几对文件）、越层引用、未归属的文件、超过 1000 行的文件，当场点名，只提醒不拦。

### 四段管道

取事实 → 连关联并绑说明 → 出页面 → 核对，段与段之间只靠一份文档模型传话。`build --facts-json` 把这份模型打出来，不出页面，排查「页面为什么这么显示」时先看它。整个 `build` 不调 AI，同样的来源和同样的说明，两次生成逐字节相同——所以页面里不写生成时间，否则每次重出都是一批没有内容的差异。

### 谁写谁读是怎么查的

只在**字符串字面量**里认 SQL：`INSERT INTO`、`UPDATE`、`DELETE FROM`、`TRUNCATE`、`COPY … FROM`、`MERGE INTO` 算写，`FROM`、`JOIN` 算读，另认 asyncpg 的 `copy_records_to_table` 一类接口。代码行里的 `from orders import …`、注释里的 SQL 不算。认不出的不静默丢：运行时拼的表名、切不动的文件各有清单。它不解析 ORM、不做调用图。

所以页面上出现「没有找到写这张表的代码」时，按这个顺序查：`codeRoots` 是不是漏了目录 → 是不是经运行时拼的表名写的（看首页那张清单，用 `dynamicTables` 归上）→ 是不是真的没人写（这本身是个值得问原作者的发现）。

### 需求规格凭什么说「一个字不少」

靠两道互不相信的检查，不靠出页面的代码写得仔细：

- **切块时的还原自检**：规格先被切成块——标题、列表项、表格行、引用、围栏、分隔线、段落。切完当场把所有块连同被去掉的记号（`#`、`-`、`3.`、`>`、表格的竖线）按原位拼回去，必须逐行等于原文件，对不上就报到第几行第几个字、退出码 3，不出半份结果。所以「切的时候丢了字」在出页面之前就拦下了。被去掉的记号里也不许夹着字——字要是被归进了记号，拼得回原文、页面上却没有，这一条专门堵它。
- **核对时把页面读回来**：核对器不 import 出页面的任何代码，自己读页面、自己去掉行内记号，再和重新切出来的块比。出页面的代码吞了一个字，重出一遍两边错得一样，靠「页面是不是现行的」看不出来，靠这一项看得出来。

分句、图、可展开的区都只是显示上的手段：断行处插的是不带字的标记；图里的字不算进正文，另有一项专门核它们都取自来源；引用为打印另备的那一份单独拿去和来源比——所以它们既不会让核对误报，也藏不住丢字、编不进字。

锚点（每一块在页面上的名字）按序取第一种能用的：条目开头带 `[REQ-…]` 编号的用编号；列表项开头是粗体词的用「章节路径 / 粗体词」；别的用「章节路径 # 本章里的序号」。给需求写上编号，锚点就稳，往后做需求到表、到模块的关联时也连得上。

### 不带出去的东西

页面上显示的每一段取自来源的文字和说明的正文，都过一遍隐去规则：内网地址、带口令的地址、密钥样式的字样会换成「〔已隐去〕」，首页顶上列出隐去了几处、各在哪。规则宁可偏紧；被误伤的地方看得见、也查得到出处。需求规格同样过这一遍——它号称一个字不少，唯一的例外就是这些，清单页顶上写明第几行隐去了几处、换掉了多少个字，核对按隐去后的文字比。

隐去只换掉口令或地址本身，不连带它后面的话：`password=Abc12345，生产环境与测试环境各一套` 只换掉那八位，后面的中文照常显示。口令关键字认 `password`、`passwd`、`secret`、`token`、`api_key` 与 `密码`、`口令`、`密钥`，值要够八位并且带数字（或够十六位）才算。形状固定的几种令牌不用关键字也认：GitHub、AWS、Google、Slack 的令牌，三段式的 JWT，以及私钥——私钥从 BEGIN 那一行到 END 那一行整块换掉。

**认不出来的也要知道**：内网域名、账号名、人名、写成一句话的口令（「管理员的口令是某某」），规则认不出。交出去之前，人要把页面过一遍，别只看隐去清单。

### 现在的边界

- 方言以 PostgreSQL 为准；库里实际的约束名（会被截断、重名会加数字）不模拟。
- 只读建表定义的文本，不连真库。
- 架构设计只认 Python 与 JS 一族（`.py`、`.js`、`.jsx`、`.mjs`、`.cjs`、`.ts`、`.tsx`）的引用，别的语言的文件按扩展名报数、不扫；接口只认装饰器写法的路由，别的框架读不出来，页面上会写「没有读出接口」；JS 里 `@/` 这类路径别名、配了基准目录的写法（`components/Button`）现在不解析，进「没解析到的引用」；前端调后端哪个接口，生成器不连，要靠模块说明去讲。
- 页面只该跟着入库的来源变，但生成器不认 git：代码根目录下不入库的产物（除了点开头的目录与 `__pycache__`）要自己在 `ignore` 里排掉，不然换一个副本 `check` 会报对不上。
- 交接之后对方手改了代码或文档，不回写、不再保证同步。
- 例子不带真实数据这一条，命令拦不住，靠写的人自觉与抽审。
- 需求规格只认常见的 Markdown 写法（标题、列表、表格、引用、围栏、分隔线、段落，行内的粗体、等宽、删除线）；别的写法（链接、图片、HTML 标签）按文字原样显示，不解释。需求与表、与模块之间的关联还没做。

| 退出码 | 意思 |
|---|---|
| 0 | 成功；`check` 是清单为空 |
| 1 | `check` 有不一致；`note confirm` 遇到已过期的说明 |
| 2 | 用法错、配置错、`note put` 整批被拒 |
| 3 | 脚本自身出错；需求规格切块的还原自检没过；`build` 的落盘前自检没过（原有页面不动） |
