## 1. progress-archive.mjs 增补

现有契约（条数线、判方向、先写后核再删、可重跑、指针行、退出码）全部不变，只加两条。

### P-1 认缩进写法的条目

- 条目形状：Done / Notes / Decisions 是 `<缩进>- YYYY-MM-DD`；TODO 是 `<缩进>- [P<数字>][<状态>][#<编号>]`。缩进是零个或多个空格、制表符，深浅按字符数比。
- 一行符合条目形状就是一条独立条目，不看缩进深浅，也不看上一行是什么。
- 续行 = 紧跟在条目后面（中间不隔空行）、不符合条目形状、缩进比该条目更深的非空行。其它不符合条目形状的行不属于任何条目，不搬。空行结束当前条目。
- 这样认是因为同一段里顶格与缩进两种写法会并存，而且都是独立条目：OFR 的 Decisions 段是 29 条顶格的新决策在上，隔一个空行跟着 160 条四空格缩进的老决策（每条下面挂三行更深的「依据 / 适用范围 / 取代」）；它的 Done 段更直接，一条顶格条目后面不隔空行就跟着 120 条四空格的老条目。只认一档缩进，缩进的那些永远搬不走（副本实测归档后 Decisions 仍有 148KB）；把「紧跟、更深、带日期」的当成上一条的子项，Done 那 120 条会被吞成一条——往后新条目一律顶格写，这种「顶格压在缩进块上」只会越来越多。四个仓的四个段里，真正挂在某条下面的带日期子项一处都没找到（2026-11-22 实测）。
- TODO 同理：已关闭的条目下面挂着一条更深的未关闭条目，那是独立条目，不跟着搬——未关闭的 TODO 永不搬。
- 搬迁时原文连缩进一个字符不改。判方向、保留线、已归档不重复追加、写后核对，对缩进写法同样成立。
- 归档文件里的缩进条目同样认：判重、核对、本批插在对应段最前面。
- 例（conflation 实况）：`    - 2026-11-20: 给用户出了导入后的核对表…` 这种四空格开头的条目，此前 `--check` 报「现有 0 条」。

### P-2 体积线

- 一段的体积 = 该段全部条目行（含续行）的 UTF-8 字节数，每行另加 1 字节换行。TODO 段只算已关闭（`DONE` / `完成`）的条目。
- 体积线（字节）：Done 16384，Notes 16384，Decisions 32768，已关闭 TODO 8192。地板（条数）：Done 10，Notes 10，Decisions 12，已关闭 TODO 5。
- 算法：先按现有条数线算出要搬的；再逐段看留下的条目，体积超线就从留下的里面最旧的一条起继续搬，直到体积 ≤ 线或留下的条数等于地板。已关闭 TODO 的「最旧」是编号最小。
- 条数线与体积线任一过线都搬。Done / Notes 的条数线仍是两段合计超 100 才触发，体积线各段各判各的。
- 某段只因体积线要搬时同样要判方向；首末条同日判断不出，整次拒绝、退出码 1、两份文件一个字节不动（现有规则）。
- 输出：人读模式每段一行，形如 `Done：现有 81 条 / 148.2KB，保留线 35 条 / 16.0KB，搬出 71 条（归档里已有 0 条）`（KB = 字节 / 1024，一位小数）。`--json` 新增 `bytes`，形如 `{"done":{"before":151756,"after":15980,"ceiling":16384},"notes":{…},"decisions":{…},"todo":{…}}`，`after` 是搬完后留下的体积（`--check` 时是预计值）；原有字段一个不少。

### P-3 最旧按日期认，不按位置认

implementer 在两份下游副本上实测撞出来的：Decisions 段的日期不是单调排的。

- 条目日期 = 条目首行 `- ` 之后的十个字符。段的排列方向仍按首条与末条的日期判，首末同日整次拒绝，不变。
- 要搬的是「最旧的那些」：先比日期，日期早的先搬；日期相同再比位置——方向是最旧在上时位置靠前的算旧，最新在上时位置靠后的算旧。段内日期单调时，这个选法与此前按位置切的结果完全一样。体积线继续往下搬时按同一个顺序取。
- 搬完后正文里留下的条目保持原有相对顺序；归档里本批条目按它们在正文里的原有相对顺序排。已关闭的 TODO 仍按编号，不变。
- 例（conflation 实况）：Decisions 段首条 11-02、末条 11-17，中间夹着 11-19、11-20；按位置搬前 66 条，会把 11-20 那条搬进归档、把更早的留在正文。

### P-4 手写的指针行不动

- 脚本自己写的指针行含「累计搬出 N 条」。只有这种才算机器指针：搬迁时被新指针替换，累计数接着算。
- 其它以 `（归档指针：` 开头的行是人手写的（老安装手工搬时留下的，常带「仍在生效的几条」这类说明），原样留在原位，一个字符不改；机器指针另起一行写在段末。
- 例（OFR 实况）：`（归档指针：2026-11-04 手工搬 10 条到 progress.archive.md「Archived Decisions」，日期 2026-10-28 至 2026-10-28；其中仍在生效的四条：…，原文见归档）`。2026-11-22 之前一搬就被换掉，这句话在两份文件里都找不到了。

## 2. plan-archive.mjs（新）

把做完的 Phase 从 DEV-PLAN.md 原文搬到 DEV-PLAN.archive.md。取代 dev-planner 迭代模式里「超过 20 个手工搬」的做法。

- 用法：`node .claude/scripts/plan-archive.mjs [--root <目录>] [--check] [--json]`。`--root` 默认 `$CLAUDE_PROJECT_DIR`，再默认当前目录；`--check` 只算不写；`--json` 只输出一份 JSON。
- 退出码：0 = 没东西要搬，或搬完且核对通过（含 `--check`、含「无 DEV-PLAN.md」）；1 = 读写或核对失败，DEV-PLAN.md 未改；2 = 参数错。
- Phase 小节 = 从匹配 `^## Phase\s+\d+[:：]` 的标题行起，到下一个 `## ` 开头的行之前（中间的空行与 `---` 分隔线跟着这个小节走）。围栏（三个反引号或三个波浪号）里的行不当标题。
- 已完成 = 标题行里有 `✅`。没有 `✅` 的小节、`## 范围外（本次不计划）` 这类非 Phase 小节永不搬。
- 触发与保留：已完成小节数超过 20，就把编号最小的已完成小节搬走、留编号最大的 20 个；之后留下的已完成小节合计体积（UTF-8 字节，每行加 1）超过 65536，从编号最小的起继续搬，直到合计 ≤ 65536 或只剩 3 个已完成小节。条数没过线、体积过线也搬。按编号不按文档位置：conflation 的 Phase 59 排在 54 前面、68 排在 67 前面，按位置搬会把较新的先搬走。编号相同的按文档顺序。
- 标题以 `## Phase` 开头却不符合上面那条正则的（`## Phase 5.x`、`## Phase A`），脚本不认、不搬；有 n 个且 n > 0 时人读输出另报一行 `编号认不出的 Phase 标题：n 个（脚本不搬）`，`--json` 里是 `"unrecognized": n`。
- 搬法（顺序不能换）：
  1. 要搬的小节原文按文档顺序追加到 DEV-PLAN.archive.md 末尾，一个字符不改；文件不存在就新建，首行 `# DEV-PLAN 归档`。归档里已经有的小节（它的每一行都能在归档里整行找到）不重复追加。
  2. 从磁盘重读归档，要搬的每一行都整行找得到才往下走。
  3. 改 DEV-PLAN.md：删掉这些小节；在 `## 已归档 Phase` 一节末尾为每个被搬的小节追加一行指针。这一节不存在时，新建在留下的第一个 `## Phase` 标题之前。
- 指针行：`- ` + 标题行去掉开头 `## ` 之后的原文 + ` → DEV-PLAN.archive.md`；该小节的 Task 条目行（`^\s*-\s*\*\*Task\s+\d+\.\d+[:：]`，围栏外）里出现过 REQ 编号（`\bREQ-[A-Za-z0-9]{1,16}-\d{2,4}\b`）时再接 `（REQ：编号1, 编号2）`，去重、按出现顺序。例：`- Phase 1: POI 维护补完 ✅（2026-10-28，PASS） → DEV-PLAN.archive.md（REQ：REQ-POI-001, REQ-POI-002）`。只取 Task 行的编号，与 plan-lint 的覆盖口径一致：正文别处提到的编号多半是「本期不做」，带进指针行就被算成已安排——OFR 副本实测因此多出 3 条「范围外声明与 Task 矛盾」。
- 标题带 `✅` 就算做完，后面跟着「待真任务验收」「回放」这类保留也照搬：标题原文留在指针行里，保留事项仍在 DEV-PLAN.md 看得见。
- 两份文件都先写临时文件再改名。任何一步失败，DEV-PLAN.md 一个字节不动。
- 测试注入点：环境变量 `PLAN_ARCHIVE_FAIL_AT=archive-write`（写归档那一步失败）或 `verify`（核对那一步失败），都走真失败的那条路、退出码 1。
- 人读输出一行：`DEV-PLAN：Phase 共 29 个，已完成 21 个 / 180.3KB，保留线 20 个 / 64.0KB，搬出 1 个（归档里已有 0 个）`。编号比最大的已完成编号小、自己却没带 `✅` 的小节有 u 个且 u > 0 时另报一行 `没标 ✅ 的 Phase：u 个（编号在最后一个 ✅ 之前，脚本不搬）`；编号更大的是还没做的，不算。是做完没标还是被跳过没做，脚本判不了，只报事实。
- `--json`：`{"command":"plan-archive","ok":true,"root":…,"total":29,"completed":21,"completedBytes":184627,"moved":1,"alreadyArchived":0,"unmarked":8,"nothingDue":false}`，`unmarked` 就是上面的 u，`--check` 时另带 `"check":true`。

### plan-lint.sh 配套

`## 已归档 Phase` 一节里的指针行（带 `→ DEV-PLAN.archive.md` 的列表行），箭头之后 `（REQ：…）` 后缀里的编号，在需求覆盖检查里算「已被 Task 安排」——归档不许把覆盖检查搬红，也不许搬绿。只认后缀、不认整行：指针行前半是标题原文，标题里常带「REQ-X 推到下期」这类编号，整行读会把它算成已安排（审查复现：搬前 rc 0、搬后报「范围外声明与 Task 矛盾」；反过来也能把「需求没人做」搬没）。指针行引用了 Spec 里没有的编号，照旧报悬空。project-status 读指针行用同一个口径。被搬走的 Phase 原先有的结构类失败（缺「验证的假设」这类字段）会跟着从 plan-lint 的输出里消失，这不算搬绿：那几条检查是给还要做的 Phase 设的，做完归档的不再追究（conflation 副本实测消失 12 行，覆盖类的行前后一条不差）。

## 3. project-status.mjs（新）

只读，一条命令回答「现在到哪了」和「三份活文档有多重」。不写任何文件，不是闸。

- 用法：`node .claude/scripts/project-status.mjs [--root <目录>] [--table] [--json]`。退出码：0 = 报告已出（文档不存在的那项写「无」）；2 = 参数错。
- 需求编号的认法与 plan-lint.sh 相同：声明 `^\s{0,1}(?:[-*+]|\d+[.)])\s*\[(REQ-[A-Za-z0-9]{1,16}-\d{2,4})\]`，引用 `\bREQ-[A-Za-z0-9]{1,16}-\d{2,4}\b`。围栏里的行都不算。
- 功能条目 = `## 功能需求` 这一段（到下一个 `## ` 为止）里的顶层列表项，即行首零到一个空格后接 `-` / `*` / `+` / `数字.` 的行；它后面缩进更深的行是它的续行。
- 第一行以 `现在到哪：` 开头，片段之间用 ` · ` 连接：
  - 有 Product-Spec.md：`需求 N 条（含推断 a、默认 b）`，a / b 是条目文本（含续行）里出现 `[推断]` / `[默认]` 的条数；`## 待定问题` 段的表格有数据行时再接 `待定 q 项`（表头行与分隔行不算）。
  - 有 DEV-PLAN.md：`Phase x/y 完成，当前 Phase N：<标题，超 30 字截断>`。y = 现存 Phase 小节数 + `## 已归档 Phase` 里的指针行数；x = 带 `✅` 的小节数 + 指针行数；指针行只认 `## 已归档 Phase` 一节里带 `→ DEV-PLAN.archive.md` 的列表行，节里别的列表行不算。「当前」是没带 `✅` 的小节里、编号比最大的已完成编号大的那些当中编号最小的一个；一个 `✅` 都没有时是编号最小的小节；没有这样的小节时写 `Phase x/y 完成，全部完成`。编号比最大的已完成编号小、自己没带 `✅` 的小节有 u 个且 u > 0 时再接 `前面 u 个没标 ✅`，这时即使没有「当前」也不写「全部完成」，整段是 `Phase x/y 完成，前面 u 个没标 ✅`（与 plan-archive 的 `unmarked` 同一个数，`--json` 里是 `plan.unmarked`；是做完没标还是被跳过没做，脚本判不了，只报事实）。有 DEV-PLAN.md 却一个 `## Phase <整数>:` 小节与指针行都没认出来（比如写成了 `### Phase 1:`）时，这一片段整个换成 `DEV-PLAN 里没认出 ## Phase 小节`，不报 `Phase 0/0 完成，全部完成`——conflation 的 133 个 Phase 只有 23 个带 `✅`，按「第一个不带 ✅」算会把早就做完的 Phase 1 报成当前。已完成小节的标题与已归档指针行里出现「回放」的合计 r 个且 r > 0 时再接 `r 个带回放待重验`。
  - 两份都没有：整行是 `现在到哪：还没有 Product-Spec.md 与 DEV-PLAN.md`。
- 第二行以 `活文档：` 开头，片段之间用 ` · ` 连接，体积一律 KB、一位小数：
  - `Spec 416.7KB`；功能条目里带修订史的有 m 条（条目文本含 `~~`、`修订：`、`修订:` 或 `取代` 任一），最长一条 L 字（字符数，含续行）——m > 0 或 L > 1500 时接 `（带修订史 m 条，最长一条 L 字）`。
  - `DEV-PLAN 232.7KB`；调 `plan-archive.mjs --check --json` 取 `moved`，大于 0 接 `（待归档 j 个 Phase）`，调不成接 `（待归档未知：<原因>）`（原因的取法见下一项）；Phase 标题行超 60 字的有 u 个且 u > 0 时接 `（u 个标题超 60 字）`。
  - `progress 630.7KB`；调 `progress-archive.mjs --check --json` 取 `moved` 四项之和，大于 0 接 `（待归档 k 条）`；调不成时接 `（待归档未知：<原因>）`——子进程退出码非 0 时原因取它 stderr 的第一行、截到 60 字，脚本不存在写「脚本不在」，输出不是 JSON 写「输出读不懂」。首末同日被归档脚本整次拒绝正是要人处理的情形，原因不带出来就没人知道该去理顺序（DEV-PLAN 那一项同样带原因）；`pinned.overCap` 为真时接 `（Pinned c/15）`；文件超过 65536 字节时再接 `（最重两段：TODO 187.3KB、In Progress 140.1KB）`——段是 `## ` 标题行到下一个 `## ` 之前，段名取标题里第一个全角或半角左括号之前的部分、去掉首尾空白，体积含标题行；第一个 `## ` 之前的内容也算一段，段名「文首」。归档搬不动的重量（未关闭的 TODO、In Progress、Risks、堆在文首的状态流水）靠这一句露出来——conflation 的副本归档后还剩 499KB，其中文首 167KB、TODO 109KB、In Progress 88KB（2026-11-22 实测）。
  - 任一「待归档」大于 0，行末接 `——先跑 /archive`。
  - 三份都没有：整行是 `活文档：无`。
- `--table`：Spec 有 REQ 声明时在两行之后输出一张表，表头 `| 需求 | 标记 | 阶段 | 状态 |`，每条声明一行。
  - 标记：条目文本里有 `[推断]` 写「推断」，否则有 `[默认]` 写「默认」，否则有 `[确认]` 写「确认」，都没有写「未标」。
  - 阶段：Task 条目行（`^\s*-\s*\*\*Task\s+\d+\.\d+[:：]`）提到该编号的 Phase，写 `Phase 3`，多个用顿号连；只在指针行 `（REQ：…）` 后缀里出现的写 `Phase 1（已归档）`（指针行前半的标题原文里提到的编号不算）；在 `## 范围外（本次不计划）` 里声明的写「范围外」；都没有写「未排」。
  - 状态：所在 Phase 全带 `✅`（已归档算带）写「完成」，部分带写「进行中」，都不带写「未开始」，范围外与未排写 `—`。
  - Spec 没有 REQ 声明时输出一行 `（Spec 未用 REQ 编号，出不了逐条表）`。

## 4. three-file-sync-gate 文案
